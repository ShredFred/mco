# P2: Expose a shared delegation lifecycle through CLI and MCP

## Classification / priority
Confirmed API capability gap; P2. MCP disconnect/cancellation behavior remains an investigation task until exercised with a fake provider; do not report a reproduced orphan-process defect.

## Evidence and failure scenario
`runtime/mcp_server.py::run_server` registers only mco_doctor, mco_review and mco_run; run/review await asyncio.to_thread synchronously. There are no session submit/status/result/cancel MCP tools. CLI in `runtime/cli.py` has session ensure/send/no-wait/result/queue/cancel/resume. MCP run output has an operational envelope, but callers cannot reconnect using a durable lifecycle receipt.
Local main/installed 0.12.1 already include newer MCP policy/model timeout resolution, progress bridging, and run_stdio_async; do not file those solved items as missing. Existing `tests/test_mcp_server.py` checks raw output and read-only selection, not lifecycle parity or lost client handling.

## Bounded change
Expose thin MCP submit/status/result/cancel wrappers over the same lifecycle service used by CLI, using 01-04 receipts. Define one versioned data schema for request/attempt identity, ticket reference, accepted/running/terminal/unknown status, cancellation confirmation, and retained artifact references; preserve transport-specific envelopes. Keep existing blocking tools compatible. Investigate MCP task cancellation with a deterministic fake and explicitly choose detach-with-receipt or scoped cancellation semantics; a disconnected call must not silently imply provider completion.

## Observable acceptance tests
- CLI JSON and MCP tools yield equivalent lifecycle fields and errors for the same fake request.
- Submit through one interface, query/cancel through the other; identity and ticket references remain stable.
- MCP client disconnect, task cancellation, timeout, and reconnect each produce the documented inspectable outcome with no duplicate fake dispatch.
- Structured conflict, unknown, pending, cancelled and failed responses remain distinguishable from a successful provider answer; transport ok must not imply execution success.
- Validate the actual registered MCP schema, not only sync helpers; all tests run without real providers.
- Retain 0.12.1 timeout/model/progress behavior when selecting the implementation base.

## Dependencies / exclusions
Depends on 01-04 lifecycle contract; integrate 05 conflict errors when available. Excludes duplicating scheduler/storage logic in the MCP layer, building a ticket service, adding broad workflow tools, and claiming that progress notifications prove liveness or completion.
