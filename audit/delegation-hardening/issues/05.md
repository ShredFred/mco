# P2: Define external write ownership and reject conflicting local writers

## Classification / priority
Confirmed missing ownership contract; P2 feature/hardening slice. Actual edit collision severity is an investigation item, not an asserted reproduced corruption bug. External worktree ownership is intentional and is not a defect.

## Evidence and failure scenario
`runtime/invocation_runtime.py::run_invocations` submits invocations to a ThreadPoolExecutor with the same repo_root. `parse_invocations` assigns the same execution scope supplied by its caller; `_run_one_invocation` passes scope and allow_paths as TaskInput metadata. `runtime/mcp_server.py::_sync_run` defaults to write and allow_paths=["."]. `runtime/execution_modes.py` maps provider write permissions, but those mappings are not an ownership lease or portable per-file enforcement. The inspected submission and artifact paths contain no owner/ticket/conflict contract. Two independent harness calls can authorize writers in the same checkout without a machine-readable collision decision.

## Bounded change
Specify an opt-in explicit write owner token and canonical external checkout identity, then implement one local conflict guard shared across cooperating CLI/MCP submissions. Start conservatively with one writer per checkout (read-only fanout remains allowed); record requested scope as metadata without claiming it is an OS sandbox. Reject owner collisions before provider start. Persist owner/ticket/base commit and lease lifecycle in receipts. Define stale lease reconciliation using proven attempt status; do not silently clear leases for uncertain running writes.

## Observable acceptance tests
- Two fake submissions targeting the same canonical checkout with conflicting owners: only one reaches adapter.run; second gets a structured conflict receipt.
- Symlink/path aliases cannot bypass checkout identity; separate externally provided worktrees can execute independently.
- Read-only fanout remains permitted; an explicit externally serialized owner flow works as documented.
- Crash/stale owner yields a reconciliation result, not automatic takeover; confirmed termination releases ownership.
- Ticket reference, owner, checkout path, base commit and requested scope round-trip to execution metadata.

## Dependencies / exclusions
Contract/investigation can begin now; implementation depends on 01 and 04 for durable identity and safe release. Excludes creating worktrees, merging branches, GitHub ticket CRUD/state changes, file rollback, distributed locking, and claims that target_paths constrain every provider tool. Do not build Orca inside MCO.
